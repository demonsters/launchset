# Decisions taken during the build

Details the spec left open, and how they were settled. One line each: what, why, spec section.
Entries marked **NEEDS REVIEW** deviate from the spec because it couldn't be done as written.

- `preview: false` disables previews and prerelease branches; it's the only way to use the `semver` build-number strategy, since validation rejects semver while previews are enabled. Why: previews are otherwise always possible (label, `workflow_dispatch`). (5, 7.2)
- `changelog.github` defaults to `true`; without a token or a match the links are simply left out. Why: matches the spec example and costs nothing without a token. (5, 12)
- iOS `plist` source takes `file` (one plist) or `files` (several). Why: "one or more Info.plist files", and `file` matches the other sources. (6.4)
- `json` and `yaml` file entries require `key`. Why: explicit beats a guessed default. (6.6)
- A `preview-plan` plan has `mode: "preview"`; the action's `mode` output keeps the four release modes. Why: one plan shape for both, as the spec asks, without pretending a preview is a release mode. (9.7, 10)
- Development and tests run on Node 26; the action bundle targets Node 24 and is smoke-tested on Node 24. (11, 13)
- `maintenanceBranches` must contain exactly one `*` (it stands for `<major>.<minor>`) and must not match `baseBranch`. Why: otherwise the version line can't be read from the branch name. (5, 8.2)
- A top-level `$schema` key is allowed in config files. Why: editor support for `launchset.config.json`. (5)
- The config loader provides `@demonsters/launchset` to TS/JS configs as a jiti virtual module. Why: the bundled action has no `node_modules`, and `defineConfig` is only a type helper. (5, 10)
- Docker `image` must not contain a tag or digest; unknown `{placeholders}` in tag templates are config errors; `tags.partial` must differ from `tags.release`. Why: catch typos early; a partial tag must never read as a release. (6.1, 9.6)
- With custom tag templates one tag name can fit several templates; classification order is partial, then marker of a configured target, then release, then other markers. Why: most specific first. (2)
- `buildNumber.offset` applies to every strategy (also `semver`); outside CI the `semver` attempt is 1. Why: migration works the same everywhere, and `launchset ship` runs by hand. (7.2, 9.8)
- The preview/prerelease base version `{next}` skips taken versions like a release does. Why: previews carry the version the release will get. (8.3)
- Branch slugs collapse repeated dashes; an empty slug is an error; an all-digit slug gets a `b-` prefix (`007` → `b-007`) so the preview version stays valid semver. (8.3)
- Changelog bullets put the PR link and author after the first summary line; bot entries show only the PR link; without a known repository a PR is written as plain `#123`. (12)
- The changelog backport is a no-op when the version's section already exists. Why: re-running finalize must be idempotent. (9.5, 12)
- Changelog heading detection covers ATX and setext headings and ignores fenced code blocks. (12)
- Changeset `source` may only be `bot` and `pr` must be a positive integer; anything else is a parse error with the line number. (4.1)
- Capacitor alias with both `build.gradle` and `build.gradle.kts` present is an error. Why: never guess which file to stamp. (6.3)
- Gradle stamping accepts only literal `versionCode`/`versionName` inside `android.defaultConfig`; dynamic values, duplicates and flavor overrides are errors that point to `gradle-properties`. (6.3)
- `regex` file entries support `$1` / `$<name>` / `$&` / `$$` like `String.prototype.replace`, after the `{version}`-style placeholders are filled; other `{…}` stays literal. (6.6)
- A `regex` entry whose `replace` uses `{buildNumber}` is stamped only by `launchset stamp` in CI, never by the release PR or the consistency check. Why: build numbers are never committed. (1.1, 6.6)
- `image` stamping skips untagged and templated references (`:${TAG}`), and fails on digest pins. Globs skip files without a reference but must match at least one. (6.6)
- JSON, YAML and lockfile stampers treat duplicate keys (or the key in several YAML documents) as ambiguous and fail. (6)
- xcconfig stamping edits only the single unconditional `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` assignment; conditional assignments are left alone; none or several unconditional ones is an error. (6.4)
- pbxproj: a selected target's configuration that doesn't set a value inherits it from the project-level configuration of the same name, and launchset then stamps that project-level configuration (once); a value set nowhere is an error. Conditional (`KEY[sdk=…]`), duplicate or `$(…)` values of a field being written are errors; configurations shared between targets are stamped once. (6, 6.4)
- Expo `versionCode` is written as a JSON integer and `buildNumber` as a JSON string. A missing key (or its `android`/`ios` object) is inserted with a minimal, indentation-matched insertion; only CI does this. (6.3, 6.4)
- The consistency check (6.7) compares marketing values only, and treats a file as consistent when stamping the expected value is a no-op. It also covers the npm lockfile and `kind: "image"` manifests (expected: the docker verify tag). (6.7)
- In CI, `launchset stamp` also writes the run's version into the root version file (and lockfile), so web builds and previews see the preview version. (6.2, 6.6)
- Several `verify` entries on one target: all must succeed; already published only if every check agrees. (7.3–7.5)
- The store-ahead error suggests a `buildNumber.offset` (the minimum that works, rounded up to two significant digits). (7.3)
- App Store Connect "already published" needs the same build number under the same marketing version; the same number under another version counts as the store being ahead. (7.3)
- Registry credentials: `LAUNCHSET_REGISTRY_USERNAME`/`PASSWORD` belong to `LAUNCHSET_REGISTRY_HOST`, or to the first image's registry, and are never sent elsewhere; other registries use the Docker config file (per host) or anonymous access; credential helpers mean anonymous access plus a note in auth errors; localhost registries use `http://`. (7.4)
- npm verify: `LAUNCHSET_NPM_TOKEN` wins over `NODE_AUTH_TOKEN`; the package directory's `.npmrc` is read before the repo root's. (7.5)
- Tags and branches are pushed with git (App token passed as an `http.<server>/.extraheader` that first resets the one actions/checkout persists); PRs, comments and releases use the REST API. Why: App pushes trigger workflows, and the end-to-end tests can use a local bare remote. (9.1, 13)
- launchset commits as `launchset[bot] <launchset[bot]@users.noreply.github.com>`, with `--no-verify` and no signing. Why: works without a configured git user or the repo's hooks. (9.3)
- Bot-PR detection looks up every commit in `<last release tag>..HEAD` (not only first-parent), deduped by PR, and keeps merged PRs whose base is the branch. Why: catches merge, squash and rebase merges alike. (9.4)
- `changelog.github` uses the earliest commit that added the changeset file, then its merged PR (preferring one into the current branch); the author is the PR author. (12)
- App Store Connect verify counts only iOS builds (platform checked by launchset; builds with an unknown platform still count). Why: one app record can hold tvOS/visionOS/macOS builds with their own numbers. (7.3)
- Credentials in an npm registry URL become a Basic header (a token wins), and URL credentials are masked in every verify message. (7.5)
- GitHub App permissions are Contents: read & write, Pull requests: read & write, **Workflows: read & write**, **Actions: read**, Metadata: read. The spec lists only Contents and Pull requests. Workflows is needed because the release branch is rebuilt from the base branch and force-pushed, and GitHub rejects App pushes that bring in `.github/workflows/*` changes without it (this also means the App key can change workflows in every repo it's installed on). Actions: read lets the preview comment list job results with the App token. Issues and Checks aren't needed. (9.1)
- Bot-PR detection lists the branch's merged PRs once (newest first, stopping at the range start) instead of one API call per commit, and starts at the current version's release commit. Why: `GET /commits/{sha}/pulls` returns only open PRs off the default branch, and per-commit calls hit the rate limit on long histories. (9.4)
- The git wrapper passes the App token to git via `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, never in argv or the git config. (9.1)
- Sticky comments are only updated when the marked comment was written by a bot account. (9.2, 9.7)
- Plans in `none` and `release-pr` mode have `buildNumber: null` and `releaseSha: ""`. (7.1, 9.3)
- publish and release-pr only run on the base branch or a maintenance branch; a `workflow_dispatch` with `version` but no `target` is an error. (9.3)
- A version that has a partial tag is never published and never gets a release tag, also after a revert brings the root version back to it. (9.6)
- Publishing or shipping a version below the latest release behaves like a maintenance release: Docker drops moving tags, the npm dist-tag is `release-X.Y`, and the GitHub Release isn't marked latest. Why: `latest` must never move backwards. (6.1, 9.3, 9.8, 10)
- A push while the current version is unfinished warns in every mode ("1.5.0 is not released (missing …); pushes don't retry it"), and the no-changeset warning only counts commits after its release commit. (9.3)
- An older unfinished version whose auto targets all have markers is released by the next finalize (release tag and Release; latest when it's the highest on the base branch; backport on a maintenance branch) instead of being superseded. (9.5, 9.6)
- Partial tags and partial pre-releases are each created only if missing and never rewritten; a partial tag without its pre-release is retried. (9.6)
- The Release body's "Manual targets" list lives between hidden markers, with its data as JSON in the start marker; shipped entries keep their first date on re-runs. (9.3, 9.8)
- The release-PR exemption of the PR check requires the PR to come from the same repository; a rename of an unchanged changeset doesn't satisfy the check. (9.2)
- The PR check diffs the merge base of the current base-branch tip and the PR head commit, not the checked-out merge commit. (9.2)
- An unreadable changeset blocks only the release PR (and `launchset version`); publish, ship and retries report it as a warning. Why: publish wins over pending changesets. (9.3)
- A commit is only the release commit when no marker or partial tag of its version sits on another commit (a pushed `git pull` merge after the release commit doesn't publish again). (2, 9.3)
- `stamp`, `verify` and `mark` check that HEAD is the plan's `release-sha`: an error in GitHub Actions, a warning locally. (9.3)
- The release PR isn't force-pushed again when the rebuilt commit has the same tree and parent as the remote branch; the same goes for the changelog backport branch. Why: no pointless CI runs or dismissed reviews. (9.3, 9.5)
- Changesets appear in the changelog in file-path order. (12)
- A dispatch on a prerelease branch makes a prerelease, not a branch preview. (9.7, 9.9)
- A PR preview builds the PR head commit (`release-sha` = `pull_request.head.sha`), not GitHub's merge commit. (9.7)
- A prerelease tag counts as taken when it exists at another commit or at our own commit (a concurrent run on the same commit); reservation retries up to 10 times with fresh tags. "Re-run failed jobs" keeps the tag (the plan is reused); "Re-run all jobs" reserves a new number. (9.9)
- `preview-comment` with an empty plan (skipped preview) is a no-op; a failed job-list read is shown in the comment instead of failing the job. (9.7)
- The prerelease GitHub Release lists the changesets added by `origin/<base>...<release-sha>`. (9.9)
- `check --push` doesn't fetch tags; every other command fetches tags when a remote exists (`--no-fetch` to skip). (11)
- `launchset version` on a branch that is neither base nor maintenance uses the base branch's rules. `mark --version` needs a released version and updates the GitHub Release only for manual targets. `hotfix` creates and pushes the branch without checking it out. `stamp` without `--build-number` writes only the version. (9.5, 9.8, 11)
- CLI exit codes: 0 ok, 1 failure, 2 usage error. Without `--cwd`, the CLI uses the nearest parent folder with a launchset config. `launchset plan` always prints JSON; `plan --preview` outside CI needs `--run-number`. `--plan` takes JSON, `@file.json`, or `LAUNCHSET_PLAN`. (11)
- The action sets `prerelease` from the channel, `pr-number` for `check` from the event, and `path` for `add`; `preview-plan` also outputs `skipped`/`skip-reason`, and `preview-comment` `comment-url`/`release-url`. (10)
- The action bundle is one ESM file built by esbuild (target node24, not minified), with jiti's CJS entry bundled (so Babel is inlined) and a `createRequire` banner; it runs next to `action.yml` without a package.json. (10, 13)
- init's "disable" never deletes a file: a workflow left without a conflict-free trigger gets `workflow_dispatch`. Unsafe shell removals become a `:` no-op with a `# launchset: disabled — <reason>` comment; heredocs and compound lines get no disable. References to removed steps/jobs are listed as manual steps. (11.1)
- init counts `name@version` tags only for the root package or a target's package; it flags unfiltered `push` workflows only when they publish or deploy; it also flags release tools (semantic-release, release-it, standard-version, release-please) and `on: release` workflows, since finalize creates GitHub Releases. (11.1)
- init keeps existing generated files (`launchset-*.yml`, `.launchset/README.md`) unless `--decide file.<path>=overwrite`, and refuses to overwrite an existing config. (11.1)
- init proposes a `tags.release` decision (default `v{version}`), makes the `package.json` next to a Dockerfile a `json` files entry of that docker target, aligns image pins decided `stamp`, and skips Dockerfiles in `.devcontainer`/test/fixture/example/docs folders. (6.6, 11.1)
- init doesn't query the stores for build numbers (no network); `verify` reports a store that is ahead and the offset to set. (11.1 step 3, 7.3)
- Converted changeset names are seeded from the source path, so re-running the conversion doesn't duplicate files; an empty Changesets summary becomes a `TODO` placeholder plus a manual step. (4.2)
- A commit whose first parent has no root version (the version file appears: adopting launchset, a root commit) is not a release commit, so merging the adoption PR doesn't publish whatever version is in package.json. `findReleaseCommit` still counts it for explicit retries. (2, 9.3)
- launchset's own previews are limited to `next/*` prerelease branches of the npm target (dist-tag `next`); PR label previews are dropped since they would never be published. (15)
- npm auth for publishing launchset is npm trusted publishing (OIDC), as spec 15 prefers: the `build` job has `id-token: write`, `npm publish` uses the workflow's OIDC token, and `verify: ["npm"]` exchanges the same OIDC token at npm (`/-/npm/v1/oidc/token/exchange/package/<name>`) for a short-lived token to read the private package; an explicit `LAUNCHSET_NPM_TOKEN`/`NODE_AUTH_TOKEN` still wins. Trusted publishing can only be configured for an existing package, so the first version is published once by hand. (7.5, 15)
  - Corrected after the v1.0.0 release failed (2026-11-18): npm's trusted-publishing tokens can only publish. Reading the package with one fails with HTTP 400 "OIDC publish authorize: Invalid token" (npm's docs: `view` and `install` "still require traditional authentication methods"). `verify` no longer does the OIDC exchange, and launchset's own npm target has no `verify`: its publish step treats "cannot publish over the previously published versions" as done, so a re-run still goes on to `mark` without an npm secret.
- The `action` target has no `verify`: scripts/publish-action.ts is idempotent (an existing `v{version}` with the same tree is a no-op, with a different tree an error). The action's major tag only moves forward (never for prereleases or older hotfixes); commit, version tag and major tag go in one atomic push. (10, 15)
- launchset's first release is 1.0.0 (the initial changeset is `major`), so `demonsters/launchset-action@v1`, which init writes into workflows, resolves from the first release. (10, 15)
- launchset's own config uses a type-only import (`satisfies LaunchsetConfig`) so it loads without node_modules in the action smoke job; other repos use `defineConfig`. (5, 15)
- The published action also contains `dist/package.json` with `{"type":"module"}`, so the ESM bundle loads even when a parent folder has a CommonJS package.json (e.g. a vendored copy). (10)
- Generated workflows add a failing "Build steps missing (<target>)" step for targets whose build steps are still commented examples (android, ios, web, custom without npm), so `mark` never records a target as shipped while nothing builds it. The team removes the step when adding their steps. (9.3, 11.1)
- The adoption skill (`skills/launchset-adopt`) ships in the npm package next to the usage skill, so it can be copied to `~/.claude/skills/` from an installed package; no Claude Code plugin manifest is provided. (16.3)
- The release workflow's concurrency group is per pushed commit (`launchset-release-${{ github.ref }}-${{ github.sha }}`, `cancel-in-progress: false`) instead of per ref as spec 9.3 says. Why: GitHub keeps only one waiting run per group, so with a per-ref group a release-commit run could be cancelled when pushes came fast, and nothing would publish. Overlapping runs are made safe instead: only the run whose commit is still the base branch's tip updates or closes the release PR, and the release (and backport) branch is pushed with `--force-with-lease`, so a slower older run can't overwrite a newer one. (9.3)
- tsdown builds the npm package with `tsconfig.build.json` (src only), so test helpers never affect the published type declarations. (13)
- Extra action outputs beyond spec 10: `marketing-version` (plain X.Y.Z for iOS), `tag`, `docker-refs-json` (the "as JSON" form of 6.1's image refs). (6.1, 10)
- `LAUNCHSET_VERSION`, `LAUNCHSET_BUILD_NUMBER` and `LAUNCHSET_CHANNEL` are exported by `stamp` as environment variables for the following steps (that's what an `app.config.js` can read), not only as outputs; for iOS the version is the plain X.Y.Z. (6.5)
- Generated bot changesets (9.4) are never written as files: the release commit would delete them in the same commit, so they go straight into the changelog section. (9.4)
- The preview workflow's `cancel-in-progress: false` for prerelease branches is an expression built from the prerelease globs (`startsWith`/`endsWith`); a branch that only looks like one also doesn't cancel, the safe direction. (9.9)
- The docs are hosted on GitHub Pages (https://demonsters.github.io/launchset/, public although the repo is private), published by `.github/workflows/docs.yml` on pushes to main; every docs link in the code comes from one constant (`src/core/links.ts`). (16.1, 17)
- **NEEDS REVIEW** The public demonsters/launchset-action repo gets a placeholder LICENSE ("Copyright (c) demonsters. All rights reserved.") because the package is UNLICENSED; the bundle also contains third-party MIT code, and `dist/index.js.LEGAL.txt` holds only the legal comments esbuild kept, not a full third-party notice. The team should pick the license text. (10, 15)
- Repos with a shared version **and** independently versioned npm packages are supported as a documented hybrid (docs "Alongside Changesets"): launchset releases the shared version, Changesets keeps the packages. No code changes: `version.file`/`changelog.file` can point at a private app package, init's Changesets machinery can be answered `keep`, and Changesets' `privatePackages: { version: false, tag: false }` keeps it off the app (with it, `changeset status` only asks for a `.changeset` file when a public package changed; checked with Changesets 2.31). The Version Packages PR skips launchset's check with a job `if` on `changeset-release/*`, not a branch filter, so a required check doesn't hang. Why: per-package versioning in launchset would reimplement Changesets and break principle 1, while public SDKs need versions of their own. (1.2, 16.2, 16.3)
- `changelog.github` is renamed `changelog.links` (host-neutral: GitHub PR or GitLab MR links). `github` stays a deprecated alias: it is accepted and mapped onto `links`, marked `deprecated` in the JSON Schema, and giving both with different values is a config error; the resolved config only has `links`. (5, 12; design/GITLAB.md phase 1)
- The CI adapter normalizes the event into `EventInfo.kind` (`pr`, `push`, `dispatch`, `other`; GitHub `pull_request`, `push`, `workflow_dispatch`, anything else incl. `pull_request_target`); flows decide on `kind` and keep the raw `name` only for messages. (9.2, 9.3, 9.7; design/GITLAB.md phase 1)
